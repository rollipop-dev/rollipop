title: MCP Server
---

Connect an [MCP (Model Context Protocol)](https://modelcontextprotocol.io) client to the dev server for build diagnostics and app logs.

## Setup

Install the optional MCP dependency in your project:

```bash
yarn add -D @devframes/agentic@1.0.0
```

Start or restart the dev server after installing the package:

```bash
rollipop start
```

Then add the MCP server to your project's `.mcp.json`:

```json
{
  "mcpServers": {
    "rollipop": {
      "type": "http",
      "url": "http://localhost:8081/__rollipop/__mcp",
      "headers": {
        "Origin": "http://localhost:8081"
      }
    }
  }
}
```

MCP access requires a loopback `Origin` header and a connection from the same machine. Use the MCP URL's origin as shown above, and adjust both ports when using custom `--port`. Binding the dev server to a non-loopback `--host` does not enable remote MCP access.

## Tool Discovery

Use the MCP `tools/list` request for the current tool names, descriptions, and parameter schemas. Raw HTTP requests must include `Content-Type: application/json`, `Accept: application/json, text/event-stream`, and the `Origin` header shown above.

| Tool                                             | Arguments                                                 | Result                                                                           |
| ------------------------------------------------ | --------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `get_build_events`                               | `duration?` (1,000–60,000 ms; default 10,000)             | Events received during the listening period.                                     |
| `get_bundler_status`                             | `bundlerId`                                               | Current build status.                                                            |
| `build_logs`, `build_errors`, `get_console_logs` | `limit?` (1–500; default 100), `bundlerId?`               | Buffered diagnostics or app logs.                                                |
| `clear_build_logs`, `clear_build_errors`         | `bundlerId?`                                              | Clear one diagnostic buffer.                                                     |
| `clear_build_diagnostics`                        | `bundlerId?`                                              | Clear both build log and error buffers.                                          |
| `clear_console_logs`                             | `bundlerId?`                                              | Clear app logs.                                                                  |
| `reset_cache`                                    | None                                                      | Clear the build cache.                                                           |
| `list_clients`                                   | None                                                      | Known HMR clients, including disconnected clients.                               |
| `reload`                                         | None                                                      | Reload connected apps and return the client list.                                |
| `get_build_info`                                 | `bundlerId?`                                              | Resolved configuration, exposed environment values, and optional bundler status. |
| `symbolicate_stack`                              | `stack`, `bundleUrl?`, `bundleName?`, `platform?`, `dev?` | Symbolicated stack frames.                                                       |

`symbolicate_stack` uses `bundleUrl` or an HTTP URL in a stack frame; that URL must include `platform` and `dev` query parameters. Otherwise, provide `bundleName`, `platform`, and `dev` explicitly.

## Build Events

### `get_build_events`

Collects events emitted after the tool call starts for `duration` milliseconds (default: `10000`, minimum: `1000`, maximum: `60000`). It does not replay earlier events, so start listening before the action you want to observe.

Returns an array of events collected during the listening period, or the message `No events received during the listening period.` when none arrive. Event types include:

- `bundle_build_started` / `bundle_build_done` / `bundle_build_failed` — build lifecycle
- `watch_change` — file change detected
- `hmr_failed` — HMR update failure
- `client_connected` / `client_disconnected` — HMR client lifecycle
- `cache_reset` — cache cleared through MCP or the dashboard
- `server_ready` — server setup completed

Bundler-scoped events include `bundlerId` in their JSON payload. This includes build lifecycle events, `watch_change`, and `hmr_failed`. Client lifecycle, server, and cache events omit `bundlerId`.

App console logs are not build events. Use `get_console_logs` for the buffered `client_log` entries captured by Rollipop.

`bundle_build_done.bundleFilePath` points to the generated bundle. Edit it to test bundle changes. Source maps are unavailable for edited bundles.

### `reset_cache`

Clears the build cache without triggering a rebuild or reloading connected apps. To start a fresh dev-server session with the cache cleared, restart with `rollipop start --reset-cache`.

## App Logs and External Debugging

Use `build_errors` for bundler warnings, crashes, and HMR failures. Use `get_console_logs` for app logs.

For CDP debugging, runtime evaluation, runtime exceptions, network inspection, or CPU/heap profiling, use [`agent-cdp`](https://github.com/callstackincubator/agent-cdp) against the Rollipop dev server target. For React component tree inspection and React DevTools profiling, use [`agent-react-devtools`](https://github.com/callstackincubator/agent-react-devtools).

Build logs, build errors, and app logs each retain up to 500 entries across builds. Their query tools return the latest 100 by default and accept `limit` (1–500) and an optional `bundlerId`. Before a focused repro, clear the relevant buffer with `clear_build_diagnostics` or `clear_console_logs` so older entries do not get mixed into the current observation.

## Bundler Status

Use `get_bundler_status` to read the current lifecycle state for a known `bundlerId` from build events.

The response is a point-in-time snapshot:

```json
{ "id": "<id>", "status": "build-done" }
```

| `status`       | Meaning                                                      |
| -------------- | ------------------------------------------------------------ |
| `idle`         | Bundler instance created but the first build has not started |
| `building`     | A build is currently in progress                             |
| `build-done`   | The most recent build completed successfully                 |
| `build-failed` | The most recent bundle build failed                          |

Unknown ids return `{ "error": "not found" }`.

HMR update failures emit `hmr_failed` without changing the build status.

## LLM Workflow

1. Clear build/app log buffers before focused checks when older diagnostics may be noisy
2. Start `get_build_events` with a listening period long enough to cover the change
3. Make code changes while the call is listening, then inspect its returned events for `bundle_build_done`, `bundle_build_failed`, or `hmr_failed`
4. Use buffered `build_logs` and `build_errors` for diagnostics when an event occurred before listening started
5. Use `bundleFilePath` from `bundle_build_done` when bundle-level debugging is needed
